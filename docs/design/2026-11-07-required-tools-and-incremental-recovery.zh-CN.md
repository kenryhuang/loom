# 必需工具闭包与增量恢复

## 问题

工作包规划器声明 `required_tools`，派发推荐器却只收到目标与验收文字。推荐器可以因“只读分析无需 shell”省略已声明的必需工具，宿主直到 worker 的 acceptance preflight 才发现不一致。旧恢复路径等待下一次周期检查，然后重建 workflow、plan、acceptance 和 context。

## 首次派发

推荐器接收必需工具清单，继续选择覆盖任务发现、执行与验证所需的最小集合。宿主在推荐或 fallback 之后补齐必需工具对应的内置 collection，并使用实际资源权限、注册插件和已绑定外部工具验证 `required_tools ⊆ assembled.bindings`。检查发生在创建/复用 Session 之前。

补齐不加载整个工具目录，不自动安装或绑定未知外部工具，也不改变只读资源权限。无法满足的合同在派发层给出具体工具 ID。推荐结果、必需工具、宿主补入的 collection 一起记录。复用 Session 必须匹配补齐后的配置。

自动调研与例行检查的 `read_only` 工作使用固定受限环境，不能沿用 Role 的 shell 能力。规划器接收与派发器使用同一校验路径计算的实际工具清单；结构化响应校验拒绝不可用的 `required_tools`，在原预算下最多纠正一次，仍不满足则不创建工作包。普通任务对只读源目录进行隔离验证的规则不因此改变。

`filesystem` 提供只读的 `list_directory`，用于分页浏览目录并配合 `read_file` 调研代码，无需 shell。目录浏览沿用工作区路径边界，不跟随越界符号链接。规划器不得自行给目录清点任务增加命令执行验收要求；确实无法完成的显式检查必须保留为未知项。已有错误工作包须重新规划，不能仅删除工具要求而保留无法履行的命令验收合同。

工具可见性预算保留工作合同与验收合同中的必需工具，以及 `tool_call` 验收所引用的工具；其余工具仍可裁剪。该保护只作用于当前 workflow 可见工具，保留路由阶段和显式节点工具限制。

## 执行中发现缺工具

缺工具暂停与 Agent 状态同事务提交时，将下一次调度设为立即到期；按 run/attempt 去重，不绕过禁用调度、人工暂停、输入等待或人工接管。worker 尚未退出时，一秒后复查，不启动并发 worker。原有恢复次数、预算、来源、归属与未知副作用检查继续生效。

纯能力缺口使用 `extend_tools → resume`：

1. 根据结构化缺口确定最小新增 collection，不调用模型重新推荐或重审验收合同。
2. 准备阶段验证真实工具可用性；提交阶段重新检查源状态、任务版本、控制指令与配置摘要。
3. 在 Resume 事务内应用仅追加工具的配置，发布配置变化与 `task.tools.extended`，保留 run、checkpoint、context、计划、验收要求、证据和累计用量。
4. worker 恢复时核对源/目标配置摘要与原插件 manifests，只初始化新增工具 collection；保留原插件状态与工具调用身份。沿用现有工具绑定更新逻辑重新考虑未执行动作，复验已有结果。
5. 迁移后的 checkpoint 与迁移标记清除一起提交。失败 run 替换时也携带迁移意图。

该路径不允许修改目标、工作目录、权限、已有插件、工具预算或删除 collection。需要工作副本、合同修订或其他配置变化的组合恢复仍使用重建路径。普通 Session 没有 Agent 调度器，不因此获得后台自动恢复。

## 回归验证

- 推荐遗漏必需工具、推荐失败回退、外部工具已绑定、未知工具、只读资源限制。
- 紧张的工具可见性预算仍保留必需工具，并裁剪其他工具。
- 缺工具即时唤醒、重复保存去重、worker 退出竞态、人工控制与禁用策略。
- 追加工具时保留计划、原证据、验收状态、计数；拒绝过期配置和非追加变更。
- 真实 worker 读取文件后追加 shell 验收要求，自动恢复后运行验证并通过：同一 run、只读取一次、只生成一次初始验收计划，无 `task.restarted`。
