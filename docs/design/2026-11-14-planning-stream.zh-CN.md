# 规划过程可见性

## 状态边界

规划调用与执行 Session 分开。一次规划可能发布阶段，也可能选择 wait、request_input 或 review_stage；不能把 committed 等同于已生成工作包。

- 准备输入、等待首个输出：规划 attempt 已创建，尚未发布任务。
- 接收草案：通过 provider.stream_chat 接收真实输出；不支持 stream 的 provider 只展示等待状态及最终草案。
- 校验与纠错：保留协议校验、拒绝、重试事件。重试使用新的 request_id，替换当前草案。
- 发布：完整响应通过协议/契约校验，且 generation、输入版本、planner lease 仍有效后，在原事务内发布 goals/work packages，记录实际发布数量与决策原因。
- 调度：工作包进入 dispatch queue，等待依赖和资源；发布不代表开始执行。

旧阶段规划器先发布 goals，后续 goal planner 再发布工作包。统一规划器一次提交整个阶段的 goals 和工作包。两条路径共享流式预览，不改变预算准入、验证和发布边界。

## 存储和展示

`agent_runs.stream` 保存当前请求、状态、attempt、模型、更新时间和各输出通道。每通道最多保存最后 6,000 字符，另存累计字符数；这是展示用尾部预览，不是模型上下文，也不是恢复执行凭据。

首个输出和结束立即写入，中间更新最多每 750ms 写一次。`plan.stream.updated` 只记录小型计数/状态，用于页面版本更新，不重复保存原文。Goals 页现有 1.5s 自动刷新读取有界快照，Planning 使用独立区块，默认折叠，摘要始终显示当前状态；展开显示实时动态，自动刷新保留用户的展开/折叠选择。每个 objective 最多显示最近三个 attempt，每个 attempt 最多二十个生命周期事件，stream 更新不挤占该事件额度。

终态 attempt 不接受迟到预览。失败保留已收到的预览，页面刷新可恢复显示；数据库写锁竞争不能因此丢弃已付费响应或重发模型请求。完整草案仍需原有校验流程确认，预览文本不能创建任务。

`agent_runs.outcome` 在发布事务中记录 action、reason、已发布数量和后续检查时间。历史记录只投影已有 decision 的 action/reason，不伪造缺失流或发布数量。

## 运行边界

前端静态资源刷新即可更新；Python 服务重启后，后续规划请求才会产生 stream 快照。历史的非流式请求不能补出逐段输出。规划发布前没有可靠完成时间，因此界面显示实际状态、输出量和更新时间，不提供虚构的百分比或 ETA。


## 结构化 Planning 展示

Planning 展开后优先展示持有 `planner_lease` 的当前运行；无当前运行时展示最近记录。其余记录放入默认折叠的历史区，每次运行可独立展开。最多返回三条记录，但当前持有 lease 的记录不会被较新的历史挤出。遗留 `planning` 状态若没有 lease，标为未结束的历史记录，不显示为正在运行。

每次运行显示所属目标/阶段、开始时间及运行标识。Stage planning 定义目标，Work package planning 为选定目标拆分执行任务，Session 承担执行；不同目标的规划属于独立运行，单次运行的模型纠错使用 Attempt 编号。历史先后顺序本身不表示替代关系。

过程只显示开始、模型请求、校验、拒绝、重试和提交等关键事件，同一 attempt 的同类事件去重。结果展示决策、Markdown 原因、发布数量及明确关联到本次运行的工作包；工作包状态标注为当前执行状态，可进入 Session。草案、模型推理及完整事件详情默认折叠，自动刷新保留展开状态。截断草案不被解析为正式结果。
