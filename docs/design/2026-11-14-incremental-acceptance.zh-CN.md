# Acceptance：可持久推进的分阶段验证

日期：2026-11-14（Asia/Shanghai）。状态：持久工作账本、分段审读、断点调度及保守依赖复用已实现；更细的义务拆解与依赖建模仍按下述边界处理。

## 实现与边界（2026-11-14）

- `acceptance_ledger.py` 保存工作身份、输入/输出 artifact、状态、attempt、成本和依赖。确定性检查、选源、页观察和最终判断都逐项提交；复用时检查凭证及传递依赖。持久性与过期 worker 隔离复用现有 execution boundary，而非另设数据库。
- `acceptance_batches.py` 保存当前批次、初验/补验阶段、固定 chunk 计划及下一页游标。恢复直接读取计划和断点；改变批大小不会重排正在执行的批次。结构化模型响应在上层批次凭证写入前也已落盘，事件投递失败不丢已提交工作。
- 默认 16 页不再充当永久总量上限；用户显式配置的 `max_evidence_pages` 仍是硬上限。`max_chunks_per_slice=8` 控制调度让出频率，不授予新预算；每次只为下一项做预算准入，累计预算和显式 Resume 规则保留。
- 大来源目录递归分区选择，每个分区的选择独立持久化；合并结果保留完整目录 artifact、遗漏数量和“选择不是覆盖证明”的标记。缺口补验有固定游标，不因 Resume 重置。
- `max_work_attempts=3` 限制相同工作重复失败；无效预算准入不消耗 attempt。观察归纳必须缩小输入，并受 `max_reduction_depth=8` 限制，不能无进展地无限压缩。
- 依赖明确的局部文件检查可以跨其他文件变化复用；动态检查到下一次 verify 时失效，独立静态项保留。语义结果仍绑定 candidate 与完整来源总体，新增反证会使其失效。未知依赖保守绑定整轮。
- UI 展示已保存工作项和已审读页数；这是已调度工作进度，不假装预知全部后续工作总量。

当前 obligation 沿用已校验合同中的 criterion，goal 继续独立复核完整原始要求和跨项一致性；尚未新增模型自动拆解合同、独立 consistency edge 规划或任意长目标文本的分段映射协议。不能装入最小请求的合同元数据仍明确阻塞，不截断、不降低要求。不同问题不能任意复用同一来源的旧摘要；目前只复用相同提取问题及已有共享批次的观察。

本地文件系统没有与服务完成提交共用的事务。实现保留完成前后的输入指纹校验和现有 worker fencing，不声称对外部进程写文件提供原子 CAS。artifact 已写入但 checkpoint 未提交的极小崩溃窗口可能重试未提交工作；模型调用不承诺 exactly-once。


## 1. 要解决的矛盾

Acceptance 要验证的是完整要求，但单次模型调用只能处理有限证据。把全部证据放进一次 verify 会触发 token/time limits；把历史压缩成一段文字，又会丢掉覆盖范围、缺口和已经完成的判断，导致重复取证。

因此，基本执行单位应从“一轮 verify 请求”改成“一个可提交、可恢复的验证工作单元”。完整性由宿主持久账本维护，模型只负责当前单元。上下文压缩后重新加载的是下一项工作及其必要证据，进度不依靠聊天历史保存。

这不能保证任意任务在任意有限预算内完成。目标是在输入稳定、证据可得且累计预算足够时推进；预算不足时精确停在断点；证据不可能满足或重复无进展时明确停止。

## 2. 当前实现及结构性边界

以下依据当前工作区代码，包括尚未提交的修改。

| 当前环节 | 已有能力 | 仍存在的边界 |
| --- | --- | --- |
| `acceptance.py:verify` | 确定性检查、语义判断、最终完成门 | 组织方式仍是一轮完整验证，非缓存分支从头执行确定性检查 |
| `acceptance.py:fingerprint` | candidate、goal、plan、文件、journal、环境整体绑定 | candidate 或局部依赖变化会让整轮 pending 失效；存在 visual/无 scope command 时整轮不可跨调用缓存 |
| `acceptance_batches.py:request` | 每次合法响应保存 artifact/checkpoint | 页进度主要通过 prompt/payload hash 缓存恢复，需要重新构造相同请求 |
| `acceptance_batches.py:run` | 复用有凭证的已通过标准，goal 独立判断 | 已完成标准较稳定，未完成标准内部仍缺显式持久工作图 |
| `acceptance_batches.py:review/pages` | 分页、页观察、分层归纳 | 先规划全部页；超过总页数上限即失败，不能以固定窗口逐段推进任意有限来源；摘要仍可能反复归纳或重新取证 |
| `acceptance_selection.py` | 有界预览、选源、记录遗漏、按缺口补证 | 完整目录及遗漏列表仍进入请求；目录本身也会变大；选源不等于证明覆盖 |
| `acceptance_budget.py` | 请求/总预算及显式 Resume 续期 | 预算按整轮规模估算，没有独立的 work item 调度与进展判断 |

已有分页、独立 goal、原始证据 artifact 和逐次 checkpoint 都应保留。需要替换的是“请求缓存承担进度模型”的职责，而非继续增加针对案例的选择或截断规则。

## 3. 持久状态：验证账本与依赖图

采用不可变 artifact 保存内容，持久账本保存索引、状态和依赖边。账本不整体塞入模型上下文，也不把全文复制进每次 checkpoint。

| 对象 | 最少记录 | 职责 |
| --- | --- | --- |
| Verification session | goal/contract revision、snapshot ID、状态、账本游标、预算累计 | 一次验收的权威状态，与 solver 对话生命周期分离 |
| Requirement / obligation | 原始要求位置、准确谓词、量词/范围、验证方法、依赖 | 防止拆分时遗漏、降低要求或替换原始语义 |
| Evidence source / chunk | 不可变内容 hash、来源/版本、范围、完整性、时间/环境约束 | 证据身份及定位；不同版本不能按路径当作同一证据 |
| Observation | 事实、反证、局限、原文定位、提取问题版本 | 已读证据的可复用观察，不具有 passed 权限 |
| Work item | 稳定 ID、类型、依赖、状态、attempt、输入/输出 ref、预算使用 | 表示下一步，不以某次批次或 prompt 文本作为身份 |
| Obligation receipt | obligation revision、结论、证据/观察依赖、覆盖、缺口、协议版本 | 可审计的局部结论，只有有效凭证才能计入通过 |
| Coverage / consistency edge | 要求映射、共享实体/数值/版本、跨项约束、结论依赖 | 支撑完整性与最终一致性判断 |

Work item 类型包括 `discover_sources`、`inspect_chunk`、`check_obligation`、`resolve_gap`、`check_consistency`、`check_goal`。batch 仅是调度优化，不改变 work item 身份。调整 batch 大小、重排或恢复时不能抹去已有结果。

Observation 可在同一来源版本、同一提取问题下共享。新问题不能假定旧摘要覆盖了未提取的事实；允许定点读取原文，并新增 observation。来源内的语义边界优先于字符切片；必须切片时保留偏移、邻接关系及未闭合片段，避免把半段 JSON/论证当完整内容。

## 4. 分阶段推进

### 阶段 A：冻结要求与证据版本

建立验收 snapshot：原始目标、约束、交付物版本、合同版本、来源目录版本。冻结指验证绑定的内容版本，不代表禁止 solver 后续修改；修改产生新 revision。

建立“原始要求 → obligations → 验证方法”的覆盖表。大的标准可以拆为小义务，但必须显式保存量词和跨项条件。例如“七个维度都有分析，且汇总一致”至少包含七个局部义务和一个汇总一致性义务。局部全部通过不能自动证明父要求等价于这些子项；需要独立覆盖复核。

原始目标/合同也可能很长：按原文区段建立映射和覆盖审查工作项，保留完整原文 artifact。不能要求每个阶段都重带全文，也不能只保留无来源摘要。跨区段约束要有独立依赖边；无法充分映射时留下 unresolved obligation。

### 阶段 B：按问题收集证据并提取观察

以 obligation 的待证事实规划证据查询，不默认把完整工具历史作为输入。优先读取稳定来源索引；目录本身按游标分页，每次保存已搜索范围、筛选条件、索引版本和下一游标。

来源目录覆盖状态与证据审读状态分开。记录 `unseen / selected / inspected / excluded_with_reason`；相关性选择只提供路线，不能将未看来源自动记成已验证。

每个 `inspect_chunk` 请求只带：局部问题、有关约束、一个有界证据窗口、必要的既有观察及明确缺口。完成后保存 observation 和定位。共享来源的要求可以共用一次提取，但不能无限增加本次提取问题。

覆盖策略必须区分：

- 存在性要求：找到满足条件且版本有效的证据可能足够。
- 全称、数量、否定性要求：必须有明确总体及扫描完成凭证，或者等价的确定性完整检查；不能用若干样本宣告通过。
- 开放世界要求：若证据边界无法封闭，应明确结论适用范围或阻塞，不能伪装穷尽。

`max_evidence_pages` 不应同时代表单次调度窗口和永久总量上限。迁移时保留现有显式配置的硬限制语义，新增 `max_chunks_per_slice` 控制每次执行窗口，另设总扫描/call/token/time 限额。扫描 100 页可以分 10 个 slice，不能借此绕过用户已有总限制。

### 阶段 C：逐义务判断并提交凭证

`check_obligation` 只消费与当前义务有关的有效观察、覆盖状态和必要原文。输出 `passed / failed / needs_evidence / blocked_external` 及结构化理由。`needs_evidence` 必须指出待证事实、来源/范围和已有观察为什么不够。

宿主校验引用、依赖版本、覆盖义务和结果结构后提交 receipt；模型对事实的判断仍是 model judgment，不能声称这些结构校验证明了语义正确。

Receipt 保存成立理由、关键值、适用范围、反证处理及原始定位。之后通常读取 receipt，无需重放此前长对话。摘要不足时按定位补读，补读不删除已完成的其他义务。

### 阶段 D：跨项一致性与目标验收

将跨项问题显式建成工作项，例如报告总数与分项总数、输入/输出版本、接口衔接、互斥结论、全局约束。它们依赖具体 receipts，并可能读取关键原文。

最终 goal 保持独立语义门，负责原始要求覆盖、整体交付是否回答目标及未闭合约束。输入为有界的覆盖凭证、局部结论、跨项结论和相关原文，不能重新加载全部原始证据。

如果 goal 材料仍然过大，继续生成有覆盖范围的 goal 子审查项，并保留父层独立覆盖/整体判断，不能只对 passed 做 AND。任意无法拆解且最小充分证据仍超过模型容量的关系，返回明确能力限制，不通过有损摘要强行通过。

最终提交由宿主检查：全部必选义务及 goal 的凭证有效、无缺口、原始要求覆盖闭合、所有跨项条件闭合、依赖版本仍匹配。以 revision/CAS 原子提交 completion，避免验证完成到提交之间的写入竞态。动态外部状态没有原子快照时，明确时效策略，不能宣称永久有效。

## 5. 中断、压缩与恢复

工作状态：`pending → running → committed`；异常进入 `retryable / waiting_budget / blocked`；依赖变化进入 `stale`。验收未做完属于执行状态，不等同于业务不满足。

每个工作项执行协议：

1. 持久化输入版本、依赖和 attempt，再执行一次有界调用。
2. 校验响应并写不可变 output artifact。
3. 在持久事务/CAS 中提交 work item、receipt/observation、后继工作和实际预算；checkpoint 引用该提交版本。
4. 提交成功后才开始下一项；对外事件由提交后的 outbox/同等机制投递，不能靠 UI 收到事件证明进度已保存。

恢复直接从账本查 ready work，不重新从头构造原 batch。压缩仅影响模型短期上下文，不能更改账本。

崩溃发生在 artifact 写入后、提交前：按稳定 work item/attempt ID 找回可校验输出；无法确认时重试该未提交项，已提交项不重做。模型请求不保证 exactly-once；要求提交幂等。命令调用也不能声称 exactly-once，副作用命令需要独立执行策略，不能因未知结果盲目重跑。

Resume 默认继续验收；只有实际发现交付缺陷才进入 solver repair。模型超时、预算耗尽、上下文压缩和缺证据本身不触发 solver 改写 candidate。

## 6. 输入变化：沿依赖边失效

保证的是“同一 revision 内进度单调”，不是永远复用旧通过结果。

- 修改某文件：失效依赖其旧版本的观察/判断，以及下游一致性/goal 凭证；无关项保留。
- 新增有关证据或反证：即使原证据 hash 未变，也要使相关结论及依赖的目录覆盖凭证失效。全称/否定性结论还依赖来源总体版本，新增来源会改变总体。
- candidate 改写：默认是新版本，不能用模糊语义相似度认定不变。仅在合同明确区分展示文本和交付内容、且依赖可追踪时，允许保留未依赖展示文本的结论。
- command/visual 等动态依赖：按工作项声明可复用条件、观测时刻与有效期；未知依赖保守扩大失效范围，不让一个动态检查强迫所有独立证据重读。
- goal/合同/验证规则变化：重新验证覆盖映射；可保留仍有效的原始证据和提取观察，旧结论不能直接冒充新规则结论。
- 依赖不完整或 artifact 丢失：相关项失效或阻塞。局部失效是依赖可追踪后的优化，未建立依赖前维持现有整体失效更安全。

所有结论的 validity 都是宿主计算，不能由模型自报“之前已经验证过”。

## 7. 防止预算与取证循环

请求预算、执行 slice 预算、验收累计预算、任务/Agent 总预算分别约束，不因阶段切换而清零。单次请求同时预留输出空间；不同 work type 使用不同输出和时限。

调度不必预留完成整个大标准的所有调用。只在剩余额度允许安全执行下一项时启动，剩余不足则落盘 `waiting_budget`。执行切片只是让出调度权；只有既有明确 Resume 规则可以续期预算。

超时重试限定次数，并按预算减小失败的未提交工作项；拆分父项保留 lineage、累计成本和覆盖并集，不能通过不断生成新 ID 重置重试次数。确定性命令超时要由对应方法处理，不能套用文本切片。

缺口 key 由义务版本、待证事实、来源版本和定位构成。相同 key 没有新增来源、覆盖或事实时，不重复相同 fetch/verify。精度不足可以有限地扩大原文窗口；达到无进展阈值后返回 `blocked_no_progress` 及具体原因。

进展度量分别记录：已完成来源扫描范围、已读 chunk、有效 observations、已闭合义务、待处理缺口/跨项关系、失效数量。调用次数增加或摘要变短不算有效进展。显示类似“本 revision 12/15 义务有效，剩余 2 个取证、1 个一致性检查；因预算暂停”，而非每次恢复都显示从 0 开始。

## 8. 落地顺序

1. 引入持久 work item/ledger，先保持现有合同、证据选择和整体 fingerprint。把确定性检查、selection、page、criterion judgment、goal 全部纳入逐项提交；由 scheduler 查询下一项。先解决中断和压缩丢失进度。
2. 将 evidence source/chunk、目录游标、observation 和缺口设为独立对象；执行窗口与总限制分离。保留原始证据，减少跨标准重复审读。
3. 引入义务覆盖和跨项依赖，再实现局部失效、动态依赖复验与 goal 分阶段审查。依赖不明时继续保守失效。
4. 更新事件/UI、预算统计与旧 checkpoint 迁移。可导入校验通过的旧 receipts；无法推断覆盖/依赖的旧页缓存不直接升级为通过结论。迁移不改写任务验收要求。

建议模块边界：`acceptance.py` 保留合同/完成门；独立 ledger/store 负责原子状态；scheduler 负责 ready work 和预算；evidence index 负责来源/chunk/查询；现有 batches 演变为有界请求执行器，不再兼任完整流程状态机。

## 9. 机制验收标准

- 在每个提交边界前后注入崩溃，恢复时已提交 work item 不产生重复付费请求，未提交项按幂等协议恢复。
- 每完成一项即清空模型会话，仅靠持久状态仍可完成同一验收。
- 同一 snapshot 修改 batch 大小、调度顺序或单次窗口，不影响既有 work item 身份和结论覆盖。
- 超过旧页数窗口的有限来源可以跨 slice 完成；显式总限额不足时保留断点，不能隐式扩额。
- 多个义务共享来源时复用适用观察；新增问题定点补读，不能错用旧摘要冒充完整覆盖。
- 修改一个局部来源只使真实依赖链失效；新增反证、来源总体变化、动态过期及全局约束变化都能正确传播失效。
- 全称要求缺最后一页、计数不全、来源选择遗漏时不能通过；目录本身超大仍可持久分页。
- 所有局部通过但跨项矛盾或原始要求漏映射时，goal 必须拒绝完成。
- 相同缺口和超时重复出现时有限终止；预算账本跨恢复保留全部已消耗量。
- artifact 丢失、重复事件、过期 worker 提交和验证后并发写入都不能制造有效完成凭证。

这些测试针对状态机、覆盖、依赖与预算不变量，不以几个失败 session 恢复成功代替机制正确性。
