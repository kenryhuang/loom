# One-Command Meta-Harness Optimization for Loom

## Status

Approved design. This document defines the orchestration and user-experience
layer that runs Loom's governed Meta-Harness lifecycle from a seed trace and a
task collection with one command.

The central decision is:

> `loom optimize` is a resumable orchestration command over Loom's existing
> evaluation, evolution, campaign, experiment, and governance APIs. It does
> not introduce a second implementation of those domains.

The primary workflow is:

```bash
uv run loom optimize \
  --trace runs/smoke-kimi-20260718-173448-193048.jsonl \
  --tasks datasets/project-audit.jsonl \
  --config config.yaml \
  --tui
```

For a valid low-risk declarative candidate, this command may run through
promotion and monitoring registration without another command. Medium-risk,
high-risk, and executable candidates stop at `awaiting_approval`.

## Relationship to the Governed Meta-Harness Design

This is an additive specification for
[Governed Meta-Harness Integration for Loom](./2026-07-18-governed-meta-harness-design.md).
That document remains authoritative for:

- campaign, candidate, experiment, frontier, and promotion contracts;
- immutable evidence and content-addressed artifacts;
- proposer visibility and candidate workspaces;
- paired experiment semantics;
- task-set isolation and one-time holdout finalization;
- candidate validation and sandboxing;
- risk classification, promotion, monitoring, and rollback;
- actor authorization, transactional stores, leases, and budget accounting.

This document adds:

- the top-level `loom optimize` command;
- a simple user-facing task format;
- automatic task normalization and deterministic task-set splitting;
- a persisted orchestration state machine;
- default configuration under the existing `config.yaml`;
- a Loom-native proposer and trial adapter composition;
- unified TUI and JSON progress surfaces;
- end-to-end error, resume, report, and acceptance behavior.

Where the documents overlap, the stricter evidence, isolation, authorization,
or governance rule from the governed Meta-Harness design wins.

## Context

The governed campaign implementation exposes the necessary domain commands and
composition points, including:

- `CampaignController.run_iteration()`;
- `PairedExperimentRunner`;
- `GovernedPromotionController.promote()`;
- candidate validation, frontier, task-set, artifact, and store services.

Those primitives intentionally expose explicit lifecycle operations. They are
useful for administration and debugging, but requiring a user to invoke every
evaluation, evolution, campaign, experiment, finalization, and governance
command manually makes the normal workflow too complex and error-prone.

The existing generic task runner already produces a trace. A user should be
able to provide that trace, a benchmark task collection, and normal Loom model
configuration, then let Loom carry the workflow to a governed outcome.

## Problem Statement

Loom needs one safe production path that composes the existing primitives in
the right order while preserving their boundaries. A shell script that chains
CLI commands would not be sufficient because it would:

- duplicate state and retry decisions outside the domain stores;
- make interruption between commands ambiguous;
- encourage parsing human CLI output as an API;
- make holdout barriers and identity changes difficult to enforce;
- risk repeating paid model calls or one-time finalization;
- give TUI and non-interactive execution different control paths.

The orchestration layer must therefore call Python APIs directly, persist its
own stage projection transactionally, and treat all existing campaign and
governance artifacts as authoritative evidence.

## Goals

- Start the complete governed optimization flow with one command.
- Accept a trace generated by `loom.task` as seed experience.
- Accept a compact JSONL task format based on `TaskRequest`.
- Deterministically derive discovery, validation, and holdout sets when the
  user supplies one task collection.
- Continue to support explicit pre-split task manifests for advanced use.
- Run seed evaluation and evolution, candidate search, paired experiments,
  finalization, governance, and monitoring registration in one state machine.
- Reuse existing Loom APIs rather than reimplementing their decisions.
- Resume after interruption without repeating completed paid operations.
- Fail before paid calls when configuration, provenance, isolation, identity,
  or budget checks are invalid.
- Keep holdout tasks and detailed holdout results unavailable to the proposer.
- Auto-promote only eligible low-risk declarative candidates.
- Present the same state through concise text, TUI, and versioned JSON events.
- Produce a final human report and a stable machine-readable result.

## Non-Goals

- Replacing the detailed campaign, candidate, experiment, task-set, or
  governance administration commands.
- Treating a single seed trace as a sufficient benchmark.
- Synthesizing trusted validation or holdout tasks from a trace.
- Relaxing task-set contamination or minimum-evidence requirements to make a
  small dataset run.
- Allowing the default proposer to modify arbitrary source code, tools,
  governance, evaluators, sandbox policy, credentials, or model identity.
- Automatically approving executable or medium/high-risk candidates.
- Waiting for an entire post-promotion monitoring TTL to elapse inside the
  foreground command.
- Distributed scheduling, multi-tenant campaign service, or remote identity
  provisioning in the first version.

## Selected User Experience

### Primary Command

```bash
loom optimize \
  --trace <trace.jsonl> \
  --tasks <tasks.jsonl> \
  --config <config.yaml> \
  [--tui | --json] \
  [--dry-run]
```

`--trace`, `--tasks`, and `--config` are required for a new optimization.
`--tui` and `--json` are mutually exclusive booleans. Without either option,
the command prints concise human-readable progress.

`--dry-run` performs the complete preflight, resolves configuration and model
profiles, snapshots task inputs, derives and checks task sets, estimates the
budget, and prints the planned optimization identity. It performs no proposer,
solver, or judge call and creates no campaign search operations.

### Explicit Task Sets

Advanced users may bypass automatic splitting:

```bash
loom optimize \
  --trace runs/seed.jsonl \
  --discovery-tasks datasets/discovery.jsonl \
  --validation-tasks datasets/validation.jsonl \
  --holdout-tasks datasets/holdout.jsonl \
  --config config.yaml \
  --tui
```

`--tasks` is mutually exclusive with the three explicit task-set options. All
three explicit sets are required together. Explicit sets are still normalized,
fingerprinted, provenance-checked, and passed through the same contamination
detector.

### Resume and Replay

The command computes an `optimization_key` from the canonical resolved input.
Running the same command again:

- resumes the matching incomplete optimization;
- returns the stored outcome for a completed optimization;
- never silently creates a second search over an already disclosed holdout.

`--new-run` may create a fresh instance only when no optimization with the same
holdout digest has crossed the holdout-unseal barrier. It cannot bypass holdout
reuse protection. After holdout disclosure, a new optimization requires a new
holdout digest, normally produced by changing the task corpus or split seed.
The first instance uses `opt_<key-prefix>`; an allowed explicit new instance
uses `opt_<key-prefix>_<instance-suffix>` while retaining the same
`optimization_key` for lineage and holdout-reuse checks.

### Approval and Inspection

The normal low-risk path needs no lifecycle subcommand. Supporting commands
are available for non-interactive operation:

```bash
loom optimize status opt_<id> [--json]

loom optimize approve opt_<id> \
  --candidate candidate_<id> \
  --identity approver
```

Approval records a governance approval; rerunning the original command resumes
from the governance barrier. The TUI exposes the same approval operation after
showing the evidence and computed risk. It does not invent a separate approval
mechanism.

## Task Input Contract

### Simple JSONL Format

The user-facing task collection is JSONL with one object per task. It is
deliberately smaller than the internal provenance manifest.

```json
{"task_id":"audit-yakdb","objective":"Audit YakDB, verify its smallest embedded smoke test, and report evidence-backed improvements.","workspace":"../workspaces/yakDB","profile":"project_audit","constraints":["Do not modify project source files."],"expected_outputs":["A Markdown report covering purpose, smoke-test result, and improvements."]}
{"task_id":"audit-fixture","objective":"Audit the fixture task runner, execute its minimum end-to-end test, and identify reliability problems.","workspace":"../workspaces/audit-fixture","profile":"project_audit","constraints":["Do not access files outside the workspace."],"expected_outputs":["An evidence-backed Markdown audit report."]}
```

Required fields:

| Field | Meaning |
| --- | --- |
| `task_id` | Unique, stable identifier within the input collection. |
| `objective` | Objective passed to the generic task runner. |
| `workspace` | Local workspace to snapshot for isolated trials. |

Optional fields:

| Field | Default | Meaning |
| --- | --- | --- |
| `profile` | `auto` | Existing Loom task profile. |
| `constraints` | `[]` | Task constraints passed to `TaskRequest`. |
| `expected_outputs` | `[]` | Required output description. |
| `risk_level` | `auto` | Task execution risk hint, not candidate risk. |
| `verifier` | `null` | Deterministic post-run verifier. |
| `metadata` | `{}` | JSON metadata retained as task evidence. |

Unknown top-level fields are rejected so that misspelled safety fields do not
silently disappear. Task IDs must be unique after Unicode normalization.

### Deterministic Verifier

An optional verifier has this shape:

```json
{
  "verifier": {
    "argv": [".venv/bin/python", "smoke_test.py"],
    "timeout_ms": 120000,
    "expected_exit_code": 0
  }
}
```

`argv` is an argument vector, never a shell command string. The executable is
resolved under the trial policy, the process runs inside the isolated trial
workspace, and stdout, stderr, exit status, duration, and timeout state become
immutable evidence. Shell interpolation and ambient working-directory fallback
are forbidden.

### Normalization to Internal Manifests

Preflight converts each user row into both a `TaskRequest` and the existing
internal `TaskManifestRow`. Loom generates the internal provenance fields:

- `owner` from the authenticated submitter;
- `source_evidence_ref` from the normalized input row and workspace snapshot;
- `use_basis` from the requested or derived task-set role;
- `project_snapshot_digest` from the frozen workspace;
- `template_lineage` from a versioned, conservative structural-lineage
  detector over the normalized task/profile shape;
- `sanitizer_version` from the snapshot and content sanitizer;
- `content` from a canonical representation of objective, constraints,
  expected outputs, verifier, and behavior-relevant metadata.

The generated manifest is published before a campaign is created. Trials never
run directly against the user's mutable workspace. Every baseline/candidate
pair receives fresh materializations of the same frozen snapshot.

### Automatic Splitting

Automatic splitting is deterministic for the task digest and configured seed:

1. Normalize and fingerprint every task.
2. Group tasks by `project_snapshot_digest` and `template_lineage` constraints.
3. Exclude from validation and holdout any evidence lineage visible in the
   seed trace or imported proposer history.
4. Assign whole groups to discovery, validation, and holdout according to the
   configured ratios using a seeded stable ordering.
5. Check minimum task and valid-pair requirements.
6. Run `validate_task_set_isolation()` over the resulting manifests.

A project snapshot may not cross a set boundary. Exact content, shared project
snapshot, shared template lineage, or token Jaccard similarity at or above the
configured threshold is contamination. The threshold may be stricter than
`0.80` but never weaker.

The lineage detector removes instance-specific workspace identifiers before
comparison. Tasks produced from one common template therefore remain in one
set; changing task IDs or project names cannot manufacture independence. If
that leaves too few independent groups, the user must supply a more diverse
benchmark rather than override generated lineage values.

The default three repetitions and minimum five valid pairs require at least two
tasks in each set, hence at least six isolated tasks and at least three
independent snapshot groups. Fifteen or more tasks across multiple independent
projects are recommended. A one-project collection fails with the structured
code `TASK_SPLIT_INSUFFICIENT`; it is not silently weakened.

The seed trace is discovery-visible evidence. Its task and workspace provenance
participate in isolation checks. If Loom cannot establish sufficient trace or
task provenance to protect validation and holdout, preflight fails closed.

## Architecture

### Layering

```text
loom optimize
    |
    v
OptimizeOrchestrator
    +-- OptimizePreflight / TaskSetBuilder
    +-- Evaluation + Evolution APIs
    +-- LoomNativeProposerAdapter
    +-- CampaignController
    +-- PairedExperimentRunner
    |       +-- OptimizeTrialExecutor
    +-- GovernedPromotionController
    +-- Monitor registration
```

The governing flow remains:

```text
proposer proposes
campaign controller validates and evaluates
governance decides and activates
```

The orchestration layer advances only when the lower-level API returns a
verified artifact reference or domain decision. It never manufactures a stage
success from log text or subprocess exit status alone.

### Package Boundary

```text
loom.optimize
  cli.py             # primary command and supporting status/approval routing
  config.py          # meta_harness parsing, defaults, and CLI overrides
  contracts.py       # immutable spec, stage, state, and result contracts
  store.py           # transactional stage events, leases, and projections
  preflight.py       # input resolution, identity, policy, and budget checks
  task_sets.py       # simple task loading, snapshots, split, and manifests
  orchestrator.py    # persisted end-to-end state machine
  proposer.py        # Loom-native proposer adapter composition
  trial_executor.py  # generic task run, verifier, and evaluation adapter
  governance.py      # bootstrap, policy, promotion, and monitor composition
  reporting.py       # result.json and report.md exports
  ui.py              # shared progress model for text, TUI, and JSON observers
```

`loom.optimize` may depend on public APIs from `loom.tasks`,
`loom.evaluation`, `loom.evolution`, `loom.campaigns`, and `loom.governance`.
Those packages must not depend on `loom.optimize`.

The top-level `loom` dispatcher adds `optimize`; existing detailed commands
remain unchanged.

### Core Contracts

Public orchestration contracts are immutable values and use versioned schemas.
Conceptually:

```python
@dataclass(frozen=True, slots=True)
class OptimizationSpec:
    schema_version: str
    optimization_id: str
    optimization_key: str
    trace_ref: ArtifactRef
    resolved_config_ref: ArtifactRef
    task_manifest_refs: tuple[TaskSetRef, ...]
    model_digests: Mapping[str, str]
    campaign_spec_ref: ArtifactRef
    identity_policy_ref: ArtifactRef


@dataclass(frozen=True, slots=True)
class OptimizationState:
    optimization_id: str
    lifecycle: OptimizationLifecycle
    stage: OptimizationStage
    aggregate_version: int
    completed_operations: tuple[str, ...]
    output_refs: tuple[ArtifactRef, ...]
    failure: LoomError | None


@dataclass(frozen=True, slots=True)
class OptimizationResult:
    schema_version: str
    optimization_id: str
    campaign_id: str
    disposition: str
    selected_candidate_id: str | None
    promotion_decision_ref: ArtifactRef | None
    monitor_ref: ArtifactRef | None
    report_ref: ArtifactRef
```

The implementation uses concrete immutable mappings such as `FrozenDict`
where required by Loom's serialization contracts. The sketch above defines
responsibility, not exact constructor ordering.

### Native Proposer

`LoomNativeProposerAdapter` implements the existing `ProposerAdapter`
protocol. It receives the imported evaluation/evolution bundle, visible
campaign history, current frontier, editable/forbidden surfaces, and measured
proposal budget. It emits `CandidateDraft` values through the existing
candidate workspace and validation pipeline.

The default search permits only declarative patches to:

- system prompt and task-profile instructions;
- tool selection or description policy;
- loop/completion policy;
- bounded solver request options admitted by policy.

It cannot change the solver model identity, provider endpoint, credentials,
evaluator, judge, task data, verifier, sandbox, governance rules, or executable
tool code. Executable candidate support is opt-in, requires a configured
sandbox, and always reaches `awaiting_approval` before activation.

### Trial Executor

`OptimizeTrialExecutor` adapts a frozen trial entry to the existing
`TrialExecution` contract:

1. Materialize a fresh baseline or candidate workspace snapshot.
2. Apply the selected immutable candidate overlay for the candidate side.
3. Build a `TaskRequest` and invoke the generic task runner API.
4. Persist the emitted trace.
5. Run the deterministic verifier when present.
6. Invoke evaluation APIs with the configured deterministic and judge profile.
7. Publish trace/evaluation references, objective metrics, token usage, cost,
   duration, and structured failure classification.

The orchestrator calls Python APIs rather than chaining Loom CLI subprocesses.
Trial workers and verifier processes may use child processes or sandboxes for
fault and permission isolation.

## End-to-End State Machine

The persisted stages are:

```text
created
  -> preflight_complete
  -> seed_analysis_complete
  -> campaign_initialized
  -> search_running
  -> search_sealed
     -> rejected                         # no eligible validation entrant
     -> validation_complete
        -> rejected                      # no candidate passes validation
        -> finalists_selected
           -> holdout_complete
              -> governance_complete
                 -> promoted | rejected | awaiting_approval
```

`failed` and `paused` are resumability lifecycles rather than successful search
stages: a non-retryable error enters `failed`, while an interrupted retryable
operation or user pause enters `paused` with its current stage retained.

Stage behavior:

1. **Preflight** resolves inputs and model profiles, verifies identities and
   policy, snapshots tasks, derives task sets, checks contamination and budget,
   and computes the optimization identity. No paid call occurs before this
   stage commits.
2. **Seed analysis** invokes evaluation on the seed trace and then evolution on
   the resulting normalized evidence. Existing compatible bundles may be
   imported by digest instead of recomputed.
3. **Campaign initialization** derives a frozen `CampaignSpec`, creates or
   restores its store, and imports the trace, evaluation, and evolution
   artifacts as discovery-visible experience.
4. **Search** asks the proposer for bounded candidate batches, materializes and
   validates drafts, runs paired discovery experiments, records every outcome,
   and advances immutable Pareto frontiers until iteration or budget limits.
5. **Search sealing** commits the frontier and validation entrant digests and
   prevents further proposal operations.
6. **Validation** evaluates admitted frontier candidates on the sealed
   validation set and selects finalists with existing objective gates.
7. **Holdout** crosses the one-time barrier, evaluates only the frozen
   finalists, and commits the signed final evidence.
8. **Governance** computes candidate risk and gates, verifies rollback and
   monitor policy, and returns `promoted`, `rejected`, or `awaiting_approval`.
9. **Monitoring registration** is a required invariant of the `promoted`
   transition and its reference is recorded in the result. Rejected and
   awaiting-approval branches do not register an active monitor. The foreground
   optimize command does not wait for the full monitoring TTL; normal future
   observations drive retain, expiry, or rollback decisions.

If all candidates are invalid, dominated, or rejected, the optimization ends
normally as `rejected` with the retained failed experience. Rejection is not an
infrastructure failure.

## Configuration

All orchestration defaults live under `meta_harness` in the existing
`config.yaml`. There is no required second campaign YAML.

```yaml
meta_harness:
  proposer_model: main
  solver_model: kimi
  judge_model: kimi_judge

  search:
    iterations: 4
    candidates_per_iteration: 2
    candidate_kinds:
      - declarative_patch
    editable_surfaces:
      - agent.system_prompt
      - agent.tool_policy
      - agent.loop_policy
      - models.solver.request_options

  tasks:
    split:
      discovery: 0.60
      validation: 0.20
      holdout: 0.20
    seed: 42
    repetitions: 3
    minimum_pairs: 5
    contamination_threshold: 0.80

  objectives:
    primary: task_success_rate
    constraints:
      max_regression_rate: 0.05
      max_cost_increase_ratio: 0.25
      max_latency_increase_ratio: 0.25

  budgets:
    max_candidates: 8
    max_llm_calls: 200
    max_wall_clock_minutes: 180
    max_cost_usd: null

  execution:
    max_parallel_trials: 2
    trial_timeout_seconds: 900
    verifier_timeout_seconds: 120
    stop_on_infrastructure_error: true

  governance:
    mode: local
    auto_promote_max_risk: low
    require_approval_for:
      - medium
      - high
      - executable
```

The loader resolves this convenience shape into the existing immutable
`CampaignSpec`, objective, budget, candidate policy, promotion policy, and
monitoring contracts before hashing or campaign creation. Resolved defaults,
not raw YAML omissions, participate in the optimization digest.

Validation rules include:

- split ratios are positive and sum exactly to one after decimal parsing;
- iterations, candidates, repetitions, pairs, timeouts, and parallelism are
  positive integers;
- the search maximum cannot exceed the candidate and call budgets;
- `auto_promote_max_risk` cannot exceed `low`;
- executable candidates require an available sandbox and approval policy;
- editable surfaces must be a subset of governance policy;
- objective constraints map to explicit hard gates;
- a finite cost ceiling is required when the provider exposes reliable cost;
- unknown `meta_harness` fields are rejected.

### Model Profiles and Request Options

`meta_harness` references existing model profiles instead of copying provider
configuration:

```yaml
models:
  kimi:
    model: kimi-k2.7-code
    max_completion_tokens: 32768
    request_options:
      reasoning_effort: high
      parallel_tool_calls: false
      stream_options:
        include_usage: true

  kimi_judge:
    model: kimi-k2.7
    max_completion_tokens: 16384
    request_options:
      reasoning_effort: high
      parallel_tool_calls: false
```

Solver and judge use distinct profiles because their invocation modes and
output contracts differ. Request construction obeys these rules:

- Loom accepts and sends `max_completion_tokens`; legacy `max_tokens` is an
  explicit configuration error.
- Provider-specific enumerations such as `reasoning_effort` are validated in
  preflight when Loom knows the allowed values.
- `stream_options` is sent only for a streaming call and is never forwarded by
  a non-stream judge/proposer call.
- Candidate changes to request options remain bounded by editable-surface,
  value, context-window, and budget policy.
- Model name, provider, base URL, API key, and secret-bearing options are frozen
  and forbidden candidate surfaces.

`--tui` controls observation only. It does not change whether judge or proposer
calls are streaming.

## Identity and Authorization

One operating-system process may coordinate all stages, but no superidentity
may authorize every domain transition. At minimum, Loom distinguishes:

```text
proposer  -> creates candidate drafts
executor  -> executes frozen trials
evaluator -> publishes evaluation evidence
promoter  -> requests and commits governance decisions
approver  -> approves medium/high/executable candidates
```

The proposer cannot promote, the executor cannot edit candidates, the
evaluator can read only frozen trial artifacts, and the promoter can consume
only authorized immutable evidence. The approver does not generate candidates
or scores.

### Local Mode

`governance.mode: local` may bootstrap separate development identities scoped
to the optimization and a local trust store. Bootstrap is completed during
preflight, before paid calls, and emits an auditable policy/identity event.
Generated identities retain distinct roles and credentials.

The optimizer does not automatically exercise approver authority. An approval
requires an explicit human TUI action or `loom optimize approve` invocation;
the approval assertion is bound to the candidate, evidence digest, policy
digest, and expected governance version.

### Production Mode

`governance.mode: production` disables identity generation and trust-store
bootstrap. Required actor references must resolve through environment variables
or an external identity provider before execution. Missing or over-broad actor
claims fail preflight.

Secret values are never written into configuration snapshots, digests, events,
reports, candidate history, or proposer-visible files. Configuration artifacts
contain behavior-relevant redacted profiles and secret reference names only.

## Persistence, Resume, and Concurrency

Each run has a movable orchestration directory:

```text
.loom/optimize/opt_<id>/
  optimization.sqlite
  optimization.json
  events.jsonl
  inputs/
    config.snapshot.yaml
    trace.ref.json
    task-manifest.jsonl
  artifacts/
    evaluation/
    evolution/
    task-sets/
    reports/
  campaign.ref.json
  holdout/
    sealed-manifest.json
  result.json
  report.md
```

`optimization.sqlite` is the transactional source of truth for orchestration
events, aggregate versions, stage leases, operation IDs, and artifact
references. `optimization.json`, `events.jsonl`, `result.json`, and `report.md`
are reproducible projections or exports. Campaign and governance stores remain
authoritative for their own domains; the optimize store records their verified
references rather than copying their state.

`optimization_key` hashes the canonical resolved configuration, trace digest,
task-set digests, model behavior digests, policy digest, and split seed. Secrets,
timestamps, output format, and TUI selection are excluded. The printable
`opt_<id>` is derived from that key, with a collision-safe stored full digest.

Every stage operation records:

- stable operation ID and input digest;
- expected aggregate version;
- actor assertion;
- budget reservation where applicable;
- durable lease and expiry;
- output artifact references;
- terminal status or structured error.

An identical completed operation returns its prior result. Reusing an operation
ID with different input fails. Expired operations are reconciled against the
lower-level store or provider idempotency record before retry. Multiple
orchestrators use optimistic concurrency and only one may commit a transition.

The first `Ctrl-C` requests a graceful pause after the current atomic commit.
The second forces process exit. Rerunning the original command restores the
projection and lower-level controllers, reconciles expired leases, and resumes
from the first incomplete operation.

## Error Model

### Input Errors

Malformed tasks, unknown configuration, invalid model options, insufficient
task groups, contamination, missing provenance, identity failure, forbidden
surfaces, and impossible budgets fail preflight. They are non-retryable until
input changes and occur before paid model calls.

### Infrastructure Errors

Provider outage, rate limit, sandbox startup failure, artifact publication
failure, and worker loss use bounded retries and the separate infrastructure
budget. Exhaustion stops or pauses the optimization according to policy; it
does not become a candidate regression metric.

### Model Protocol Errors

Truncated tool arguments, malformed structured output, and invalid schema
responses preserve the raw provider response and use bounded protocol retries.

- Repeated solver protocol errors inside a trial are candidate behavioral
  evidence.
- Judge or proposer protocol errors are infrastructure failures because they
  cannot be allowed to improve or reduce a candidate score.

The role of the failing call, not only the provider exception class, determines
the classification.

### Candidate Behavioral Failures

Task failure, verifier failure, context overflow caused by the candidate,
candidate timeout, tool misuse, and invalid final output are valid paired
experiment outcomes. They remain visible in discovery history and do not abort
the campaign.

### Governance Blocks

Insufficient evidence, failed gates, risk requiring approval, stale baseline,
or absent human approval produces a governance disposition. `rejected` and
`awaiting_approval` are domain outcomes rather than generic process failures.
Digest drift, unauthorized access, or approval conflicts freeze the affected
operation and emit a high-severity governance error.

## Holdout Confidentiality

Preflight publishes a sealed holdout manifest containing opaque task
references, provenance, and digests. The proposer workspace, discovery history,
validation history, candidate artifacts, and TUI search views cannot resolve
holdout task content.

The holdout barrier may be crossed only after:

- proposal and discovery leases are closed;
- search is sealed to an expected frontier digest;
- validation results and finalist digest are committed;
- the campaign-wide holdout lease is acquired.

After unsealing:

- only the Holdout Executor can resolve task content;
- only frozen finalists can run;
- no proposal or discovery operation may start;
- infrastructure retries use the same sealed tasks and frozen conditions;
- detailed results are withheld from proposer-visible history;
- governance receives a signed summary and referenced evidence;
- future optimization may not reuse the disclosed holdout digest.

Changing output mode, retrying a command, or using `--new-run` cannot reset the
barrier.

## TUI, JSON, and Exit Semantics

Text, TUI, and JSON are observers and controllers over one orchestration state
machine. They do not implement separate workflows.

The TUI displays:

```text
Preflight -> Seed Analysis -> Search -> Validation -> Holdout -> Governance
```

Required views include:

- current stage, elapsed time, lease state, and remaining budgets;
- task normalization, split counts, fingerprints, and contamination outcome;
- baseline/candidate paired trial progress;
- candidates, lineage, metrics, frontier membership, and rejection reasons;
- holdout sealed/unsealed state without hidden content;
- computed risk, gates, evidence references, and governance disposition;
- pause, cancel, and explicit approval controls.

`--json` writes a versioned event stream suitable for automation. Human text
and TUI labels may evolve, but JSON event types and terminal result schema are
compatibility contracts.

Exit codes are:

| Code | Meaning |
| --- | --- |
| `0` | Normal terminal result: `promoted` or `rejected`. |
| `1` | Input, infrastructure, integrity, or unrecoverable process failure. |
| `2` | `awaiting_approval`. |
| `3` | Gracefully paused. |

The full domain disposition is always available in `result.json`; callers must
not infer promotion from exit code zero alone.

## Reports

Every terminal or approval-blocked optimization exports:

```text
.loom/optimize/opt_<id>/result.json
.loom/optimize/opt_<id>/report.md
```

The report contains:

- resolved objective and frozen condition digests;
- seed trace diagnosis and evolution signals;
- task-set provenance, counts, and isolation result;
- search space, candidate hypotheses, lineage, and validation outcomes;
- paired discovery/validation metrics and uncertainty;
- frontier and finalist selection reasons;
- holdout summary;
- risk classification, gates, rollback, and governance decision;
- promotion and monitor references, or exact rejection/approval next action;
- budget estimates and actual usage.

Reports link to artifacts; they are not authoritative evidence themselves.
Sensitive values and hidden holdout content are redacted.

## Testing Strategy

### Unit Tests

- Strict simple-task JSONL parsing and canonicalization.
- Workspace snapshot and task provenance generation.
- Stable grouped task splitting for the same seed.
- Split insufficiency and all contamination reasons.
- Optimization key inclusion/exclusion rules.
- Configuration defaults and strict validation.
- Legacy `max_tokens` rejection.
- Streaming versus non-stream request-option routing.
- State transitions, operation replay, leases, and projection rebuilding.
- Holdout visibility and unseal barrier checks.
- Actor permissions and approval binding.
- Error classification by call role.
- Exit-code and result serialization.

### Integration Tests with Fake Providers

- Low-risk declarative candidate reaches automatic promotion.
- Regressing or gate-failing candidate ends as rejected.
- Medium/high-risk candidate reaches `awaiting_approval`.
- Executable candidate always requires approval.
- Explicit approval resumes governance and promotion.
- Interrupted execution resumes without repeating completed model calls.
- Expired trial leases reconcile without duplicate experiment evidence.
- Verifier failure is candidate evidence, not infrastructure failure.
- Provider failure uses bounded retry and never enters the frontier.
- Invalid input fails before any fake-provider call.
- Holdout execution permanently closes proposal/search operations.
- Repeated identical command returns the same stored outcome.
- TUI and JSON observers see the same stage/event sequence.

### End-to-End Tests

A local deterministic end-to-end fixture runs:

```text
seed trace
  -> evaluation
  -> evolution
  -> candidate proposal
  -> validation
  -> paired discovery trials
  -> frontier
  -> sealed validation
  -> finalist selection
  -> one-time holdout
  -> governance
  -> final report
```

The fixture corpus contains enough independent workspace snapshots to satisfy
minimum pair and isolation rules. It exercises both automatic splitting and
explicit task sets.

A real-provider smoke test is opt-in through explicit environment configuration
and is excluded from default CI. It must use a dedicated low-cost dataset and
must not weaken the deterministic fake-provider coverage.

## Acceptance Criteria

The feature is complete when:

- a user can run the full normal path with one `loom optimize` command and
  trace, task, and existing Loom configuration inputs;
- low-risk declarative candidates require no manual intermediate commands;
- medium/high/executable candidates cannot activate without human approval;
- invalid configuration, provenance, identity, or task isolation fails before
  paid calls;
- the same command safely resumes and never repeats a completed paid operation
  or a completed holdout evaluation;
- proposer-visible artifacts never contain holdout tasks or detailed results;
- task trials use fresh materializations of frozen workspace snapshots;
- the implementation composes existing campaign, experiment, evaluation,
  evolution, and governance APIs rather than parsing their CLI output;
- `max_completion_tokens` is the only supported completion limit field;
- non-stream calls never send `stream_options`;
- all official decisions reference immutable artifacts, digests, actors, and
  operation IDs;
- TUI and JSON use the same stored state and event stream;
- final `result.json` and `report.md` explain the outcome and evidence;
- the unit, integration, and deterministic end-to-end test suites pass.

## Consequences

### Benefits

- The safe path becomes the easiest path for users.
- Existing explicit domain contracts remain inspectable and reusable.
- Interruption, retry, budget, and holdout behavior become centrally coherent.
- A simple task format makes benchmark construction practical without exposing
  internal provenance mechanics.
- Detailed commands remain available for operators and debugging.

### Costs

- Loom gains another persisted aggregate and reconciliation responsibility.
- Reliable workspace snapshots and task provenance become prerequisites for
  optimization.
- Local identity bootstrap and production identity resolution need separate
  test paths.
- End-to-end runs remain inherently expensive; dry-run and hard budgets are
  therefore mandatory design elements.

## Final Decision

Loom will add `loom optimize` as a native, resumable orchestration layer. It
will accept a seed trace and either one simple task collection or three explicit
task sets, resolve defaults from `config.yaml`, and drive the existing governed
Meta-Harness components to promotion, rejection, or approval.

The implementation must preserve strict role separation, paired evidence,
one-time holdout confidentiality, deterministic governance, and rollback-ready
promotion. Convenience is delivered by composition and durable orchestration,
not by weakening the underlying contracts.
