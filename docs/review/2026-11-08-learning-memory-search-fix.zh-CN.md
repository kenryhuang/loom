# Learning 记忆搜索修复与复测

日期：2026-11-08。问题背景见[诊断报告](2026-11-08-learning-memory-search-performance.zh-CN.md)，原始计时、数量和结果哈希见[基准数据](2026-11-08-learning-memory-search-benchmark.json)。

## 已修复

1. `MemoryStore._records()` 先用物化 CTE 按评估任务提取元数据和记忆 JSON，再展开记录。按 ID 读取时，先限制 evaluation_id，避免加载其他评估。记录和人工标注在同一只读事务内读取。
2. Library 不再复用运行时最新 500 条候选上限，可以搜索和分页到完整作用域内的有效历史。运行时 search 仍保留原候选上限、排序、去重和提示长度约束。
3. 增加服务内 `MemoryLibraryCache`，按数据库文件身份、规范化工作区/Session 和现有 `memory_versions.effective` 版本复用读取结果。筛选和翻页在同版本数据上执行；并发 Library 请求合并扫描。发布、人工标注和 Session 删除更新版本后，下一次读取重新构建。无版本表时不缓存，读取异常不返回旧结果。
4. 缓存最多 4 个作用域，按序列化数据体积限制为 32 MiB，超限结果不保留。此额度不是 Python 堆内存的精确上限。返回页面深拷贝，避免 Agent 自己的 annotation_revision 或嵌套证据被调用方修改后污染共享缓存。
5. Library 获取人工标注 revision 使用只读事务，不再申请写锁。
6. 前端每次筛选使用独立取消信号，旧响应和旧错误不能覆盖最新结果。Agent 详情更新保留 Library DOM、筛选、结果和未完成请求；只有记忆版本变化才安排自动重查，查询中发生的版本变化合并到完成后刷新。离开标签或更换作用域时仍取消请求并清理组件。

此次没有新增数据库表或迁移，也没有改变人工确认、纠正、拒绝、恢复的生效规则。

## 同一数据副本复测

使用生产数据库的一致只读快照复制相关表到独立文件，未运行迁移、调度器或模型任务。旧实现取自修改前源码，新旧候选读取使用同一个副本。

| 候选读取 | 耗时 | 完整结果 |
| --- | ---: | --- |
| 修改前 | 16.44 秒 | 与修改后逐项相同 |
| 修改后 | 1.33 秒 | 与修改前逐项相同 |

Library 现返回作用域内 4,043 条通过校验的记录；SQL 原始计数有 4,048 条相关类型已发布记录，其中 5 条未通过既有校验。原页面只统计最新候选窗口中的 499 条。分页正确性变化是有意修复，不能把新旧 Library 的总量当作完全相同的查询语义。

首次构建完整缓存约 3.06 秒；不使用缓存的完整 Library 读取约 1.9–2.4 秒。缓存首次构建还包含序列化计量成本。单作用域缓存数据按序列化计约 20.65 MB。

同版本缓存命中，每种条件 10 次采样，包含读取及 JSON 序列化：

| 操作 | P50 | 最大值 |
| --- | ---: | ---: |
| 全部 | 26.5 ms | 27.4 ms |
| Facts | 24.7 ms | 48.6 ms |
| Human reviewed | 7.3 ms | 7.8 ms |
| 无匹配关键词 | 219.4 ms | 256.8 ms |
| 下一页 | 27.9 ms | 31.3 ms |

这些是固定版本副本上的缓存命中时间。运行服务内有新评估保存或人工标注时，会重新构建；现有记忆版本是全局版本，不是逐工作区版本，其他评估更新也可能使缓存失效。不能把命中时间承诺为所有真实请求的耗时。

## 浏览器验证

用真实前端和新后端读取同一个独立副本，通过临时只读 HTTP 服务测试；没有启动后台模型，POST 禁用。浏览器观察到：

- Learning 首次内容可见约 2.86 秒，记忆 HTTP 请求约 2.53 秒。
- Facts 筛选至结果可见约 67 ms；Human reviewed 约 21 ms；未审核约 60 ms。
- 下一页至结果可见约 149 ms。
- 闲置等待 3.2 秒、跨过两次轮询后，额外记忆请求为 0。
- JavaScript 错误为 0。

上述浏览器时间是单次采样，环境与诊断时保持后台运行的生产 HTTP 测试不同。针对“后台详情变化时保留未完成搜索”和“记忆版本变化时合并刷新”，另有可控异步响应回归测试覆盖。
