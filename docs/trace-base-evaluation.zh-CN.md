# Trace analysis：Base evaluation

Base evaluation 对固定的 trace 快照做事实统计，不调用模型，也不读取当前工作区。意图识别、计划合理性、行为效率和根因分析交给 Deep evaluation。

页面和 CLI 报告采用相同的五部分结构：

1. 基础信息：原始/分析事件数、逻辑步骤与启动尝试、调用数、输入/输出/总 token、运行时验收。
2. 工具调用：按工具、类别、用途分组，展示结果分类、失败原因、耗时、截断、明确关联的重试和相同输入重复调用。
3. 时间成本：运行、暂停、等待输入、排队等状态区间；运行期间再区分仅模型、仅工具、重叠和未归类时间。
4. 模型与 token：按模型、用途、已记录阶段统计调用、耗时、token 和 usage 覆盖率。
5. 产出与完整性：记录的 artifact 和文件路径、中断记录、缺失 usage/时间/证据、无法归属的调用和时钟异常。

支持整个快照或单个 run 查看。`base.statistics` 是统一事实结构，版本为 `loom.base-facts.v1`；旧 `base.metrics` 保留兼容。Evolve/Deep evaluation 的 bundle 使用同一份事实基础。

## 统计口径

- 原始事件包含流式增量；服务分析输入过滤流式事件，两者都固定在分析 cursor。离线分析以源文件实际内容为准。
- 逻辑步骤按 run、trace、step number 识别，恢复运行后的再次启动计入尝试数。
- 工具成功/失败/取消/未结束/未知互斥。非零退出码通常失败，但明确的 `no_match` 不算失败；超时属于失败原因。成功率分母只包含成功和失败，没有已判定调用时显示“—”。
- 相同输入重复调用只记录事实，不自动认定为重试或浪费；重试要求明确的 `retry_of` 关联。
- token 采用 provider 上报值，重复完成记录不重复累计；缺失或冲突不是零。输入、输出、总量分别展示已知值与覆盖率。
- 调用耗时优先使用记录的 duration，否则使用有效起止时间。缺失或倒序时间不补零。P95 采用 nearest-rank，并展示有效样本量。
- 暂停、排队和等待输入从运行区间中分开。多个 run 的耗时之和与 session 首尾跨度分别显示。
- 模型与工具累计耗时可能重叠。时间分布通过区间扫描去重，重叠也包括 finish 等控制工具内部等待验收调用的情况。验收属于用途维度，不能再加到模型/工具时间上。
- 未归类时间不等同于框架开销。缺少记录时保留未知；provider 内部重试、精确首 token 延迟、缓存/推理 token 分项和金额目前不计算。
- 验收展示已记录的检查内容、理由、方法和结果。模型检查仍然是模型判断；保存了证据不等于验收通过。Base 页面不再并列展示一个默认的 unverified 结论。

统计实现集中在 `evaluation/base_metrics.py`，token 复用 `evaluation/token_ledger.py`。本次更新提升服务分析与行为分析版本，重新请求分析时生成新缓存，历史报告仍可读取。
